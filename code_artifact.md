# Техническое задание (ТЗ)
## Кроссплатформенное мобильное приложение для локального управления BLE-устройствами (аналог LoveSpouse)

**Рабочее название:** PulseLocal *(условное, может быть изменено)*  
**Целевые платформы:** iOS (15.0+), Android (10.0 / API 29+)  
**Тип приложения:** Полностью автономный (Offline-First) мобильный клиент без регистрации, телеметрии и облачных подписок.

---

## 1. Общие сведения и цели проекта

### 1.1. Цель разработки
Создать лёгкое, эстетичное и быстрое кроссплатформенное мобильное приложение, заменяющее официальный клиент LoveSpouse в части локального управления устройствами. Приложение должно исключать избыточный функционал (регистрацию, социальные вкладки, рекламу, платные подписки, онлайн-чат, мини-игры и голосовое управление) и обеспечивать стабильную передачу команд на устройства через BLE Advertising на обеих мобильных ОС.

### 1.2. Ключевые принципы
* **Zero-Friction & Offline-First:** запуск сразу на главный экран без авторизации; все режимы управления работают полностью без интернета. Сеть используется опционально и однократно — только при импорте профиля новой игрушки по коду/штрихкоду.
* **Единая кодовая база UI и логики:** одинаковый пользовательский опыт на iOS и Android при сохранении нативной реализации BLE-слоя для каждой платформы.
* **Dark-First & Приватность:** тёмный OLED-интерфейс для комфортного использования в темноте, локальное хранение данных, защита входа и экстренная остановка в одно действие.
* **Прозрачность протокола:** честная индикация отправки команд (`TX`) вместо имитации двустороннего Bluetooth-соединения.

### 1.3. Осознанно исключённый функционал (Out of Scope)
* Регистрация, аккаунты, облачная синхронизация и удалённое управление через интернет/WebSocket.
* Голосовое управление (Voice Control).
* Встроенные мини-игры (Game Mode).
* Социальные функции, ленты, AI-компаньоны и монетизация.

## 3. Требования к UI/UX и дизайн-системе

### 3.1. Визуальный стиль
* **Цветовая палитра (OLED Dark по умолчанию):**
  * Основной фон: `#09090B` (глубокий чёрный для OLED-матриц).
  * Карточки и поверхности: `#141418`, разделители и обводки: `#222228`.
  * Основной текст: `#FAFAFA`, вторичный текст: `#A1A1AA`.
  * Динамический акцент: настраиваемый пользователем (по умолчанию плавный переход от спокойного индиго `#6366F1` на низкой мощности к кораллово-красному `#F43F5E` на пиковой интенсивности).
  * Сигнальный цвет кнопки СТОП: приглушённый красный `#DC2626`.
* **Эргономика одной руки:** все основные элементы управления, сетки режимов, слайдеры и док-панель располагаются в нижних 65% экрана.
* **Тактильный отклик (Haptics):** лёгкая вибрация смартфона при переключении режима, нажатии `Hold-to-Boost`, старте записи и усиленный двойной импульс при нажатии `СТОП` (отключается в настройках).
* **Динамическая визуализация:** активная кнопка режима или фон области управления мягко пульсирует в такт текущему уровню интенсивности (отключается в настройках).

### 3.2. Описание экранов

#### 3.2.1. Вкладка «Устройства» (Главная)
* Отображает список или 2-колоночную сетку добавленных устройств.
* На карточке устройства: локальная иконка/фото, название, бейджи каналов (например, *Вибрация*, *Нагрев*, *Вакуум*), код модели (если есть).
* Долгое нажатие (или меню `⋮`) по карточке: переименовать, редактировать каналы/команды, дублировать, удалить.
* В правом нижнем углу (или в шапке) — кнопка «+» для добавления нового устройства.
* Если список пуст — лаконичный Empty State с двумя кнопками: «Добавить по коду / QR» и «Выбрать из оффлайн-базы».

#### 3.2.2. Экран добавления устройства
1. **По коду / QR (требует интернет однократно):** поле ввода 4-значного (или произвольного) кода с коробки + кнопка запуска сканера QR/штрихкодов (камера). После получения ответа от API отображается превью найденной модели (название, картинка, список режимов) и кнопка «Сохранить локально».
2. **Оффлайн-база пресетов:** список готовых универсальных профилей, сгруппированных по известным семействам префиксов и типам устройств (1 мотор, 2 мотора, вибрация + вакуум, вибрация + нагрев).
3. **Пустой / Ручной профиль:** создание устройства с ручным указанием имени и 8-байтового префикса (для дальнейшего наполнения через Debug Mode).

#### 3.2.3. Экран управления устройством
* **Верхняя панель (AppBar):** кнопка «Назад» (при выходе опционально шлёт `СТОП`), название текущего устройства, кнопка **OLED-замка (🌙)**, кнопка быстрого перехода к настройкам этого профиля.
* **Переключатель режимов:** горизонтальный скролл-бар с чипами (`Пульт`, `Жест`, `Ритмы`, `Сенсоры`, а также включённые опциональные модули `Кегель`, `Видео`).
* **Рабочая область:** содержимое выбранного режима (подробно описано в Разделе 4).
* **Закреплённый нижний док (всегда поверх рабочей области):**
  * Слева: индикатор `TX ●` (кратковременно загорается при отправке BLE-пакета) + таймер текущей активной сессии (`00:00`).
  * По центру: кнопка `● REC` (запись/остановка записи текущей последовательности команд).
  * Справа: крупная кнопка `■ СТОП` (мгновенная остановка всех каналов устройства).

#### 3.2.4. Оверлей «OLED-замок» (🌙)
Критически важный элемент для ночного использования и работы на iOS (где сворачивание приложения или блокировка экрана останавливают передачу `ServiceUUIDs`):
* Перекрывает весь интерфейс абсолютно чёрным фоном (`#000000`) и удерживает экран активным через системный `Wakelock` / `isIdleTimerDisabled = true`.
* Отображает сверхтусклые часы, индикатор активного режима и полосу разблокировки (долгий тап 1.5 сек или свайп вправо).
* Блокирует случайные касания.
* Аппаратная кнопка «Громкость вниз» (если включено в настройках) остаётся активной и мгновенно отправляет приоритетную команду `СТОП`.

#### 3.2.5. Вкладка «Профиль»
* **Внешний вид:** выбор акцентного цвета, включение/выключение анимации пульсации, включение/выключение Haptic Feedback.
* **Функции и модули:** переключатели отображения опциональных режимов (`Кегель`, `Локальное видео`), настройка авто-остановки устройства при выходе с экрана управления.
* **Приватность:** включение блокировки приложения (PIN / FaceID / TouchID), тумблер «Громкость вниз = Экстренный СТОП», смена иконки и отображаемого имени приложения (Stealth Mode, например на «Утилита» / «Таймер»).
* **Данные:** экспорт всей базы (устройства, кастомные команды, записанные ритмы, настройки) в один `.json` файл и импорт из `.json`.
* **О приложении:** номер версии; скрытый вход в **Режим разработчика (Debug Mode)** по 5 последовательным нажатиям на номер версии (после разблокировки появляется отдельный пункт меню и тумблер).

## 4. Функциональные требования

### 4.1. Режим «Пульт» (Classic)
* Если у устройства более одного канала (например, «Вибрация» и «Нагрев» или «Мотор 1» и «Мотор 2»), сверху отображаются вкладки или независимые блоки переключения каналов.
* Сетка плиток (3 в ряд) со всеми режимами текущего профиля (базовые скорости + штатные паттерны прошивки + пользовательские/скрытые режимы, добавленные через Debug Mode).
* Кнопка **Hold-to-Boost (Power Hit):** во время удержания пальца отправляет команду максимальной интенсивности (`intensityStepsHex.last`); при отпускании возвращает предыдущую активную команду (или `СТОП`, если до этого устройство было остановлено).

### 4.2. Режим «Жест» (Draw & XY-Pad)
* **1D-режим (для одноканальных устройств):** полотно, на котором пользователь рисует пальцем непрерывную кривую во времени; координата $Y \in [0, 1]$ преобразуется в уровень мощности.
* **2D XY-пэд (для двухканальных устройств):** ось $X \in [0, 1]$ управляет каналом 1, ось $Y \in [0, 1]$ — каналом 2.
* **Зацикливание (Loop):** кнопка фиксации нарисованного трека — после отпускания пальца траектория воспроизводится по кругу с настраиваемым множителем скорости (`0.5x`, `1.0x`, `1.5x`, `2.0x`).
* Возможность сохранить текущий зацикленный жест в библиотеку «Ритмы».

### 4.3. Режим «Ритмы» (Запись и Автопилот)
* **Библиотека ритмов:** список локально сохранённых паттернов (созданных через глобальную кнопку `REC` в любом режиме или из режима «Жест»).
* **Live-запись (`REC`):** записывает поток событий `(timestampMs, channelId, cmdHex)` с точностью до $50\text{ мс}$. По окончании записи предлагает задать имя, подрезать пустоту в начале/конце и сохранить.
* **Воспроизведение:** запуск, пауза, зацикливание (Loop), регулировка скорости (`0.5x – 2.0x`).
* **Автопилот (Wave / Chaos):** процедурный генератор паттернов без ручного ввода. Пользователь выбирает форму (Плавная волна, Пульсация, Нарастание/Edging, Случайный хаос), диапазон мощности (`min..max`) и темп. Движок генерирует нормализованный сигнал $u(t) \in [0, 1]$ и квантует его в команды устройства.

### 4.4. Режим «Сенсоры» (Shake, Микрофон, Музыка)
* **Тряска (Shake):**
  * Чтение данных акселерометра; расчёт модуля ускорения за вычетом гравитации.
  * Экспоненциальное сглаживание для устранения дребезга:
    $$S_t = \alpha \cdot X_t + (1 - \alpha) \cdot S_{t-1}$$
    где $\alpha \in (0, 1]$ регулируется ползунком «Плавность».
  * Настройка чувствительности (Gain) и локальная кнопка блокировки касаний на время активной тряски.
* **Микрофон (Ambient Sound):**
  * Захват PCM-потока с микрофона устройства (локально, без записи аудио на диск и без отправки в сеть).
  * Расчёт скользящего уровня громкости (RMS в дБ).
  * Ползунок **Noise Gate (порог шума):** сигналы ниже порога маппятся в `0` (`СТОП`).
  * Тумблер **AGC (автонормализация):** подстройка под общую громкость окружения.
* **Локальная музыка:**
  * Выбор локальных аудиофайлов (`MP3`, `M4A`, `WAV`, `FLAC`) из памяти устройства и встроенный мини-плеер (Play/Pause, перемотка, плейлист).
  * Выделение огибающей амплитуды / низкочастотного диапазона ($40\text{--}150\text{ Гц}$) через локальный FFT/декодер PCM в реальном времени и маппинг на ступени интенсивности устройства.

### 4.5. Опциональные модули (включаются в «Профиле»)
* **Таймер Кегеля:** настраиваемый интервальный таймер (*Сжатие → Удержание → Отдых* + количество повторов). Подаёт мягкие команды на устройство в фазе сжатия/удержания и `СТОП` в фазе отдыха.
* **Локальное видео:** воспроизведение видеофайлов из памяти телефона с полупрозрачным сворачиваемым оверлеем кнопок режимов. Поддерживает два дополнительных источника синхронизации: по звуковой дорожке видео и импорт локальных файлов `.funscript` (JSON-массив `actions: [{at, pos}]`, где `pos` $\in [0, 100]$ преобразуется в ступень мощности).

### 4.6. Режим разработчика (Debug Mode)
Доступен только после активации в «Профиле». Содержит 4 инструмента:
1. **Сыщик команд (Command Hunter):**
   * Выбор целевого устройства или произвольного 8-байтового префикса (из списка известных или вручную).
   * Пошаговый перебор 3-байтовых команд по банкам/диапазонам (кнопки `Предыдущая`, `Отправить текущую`, `Следующая`, автоперебор с настраиваемой паузой $1\text{--}5\text{ с}$).
   * Кнопка «Работает! Сохранить в профиль» — позволяет сразу присвоить найденному HEX-коду имя, канал, тип (ступень интенсивности или пресет) и добавить в карточку устройства.
2. **Ручной HEX-инжектор:** поля для 8-байтового префикса, 3-байтовой команды и длительности передачи (мс) + кнопка отправки.
3. **Инспектор пакетов:** live-лог последних отправленных пакетов с отображением:
   * Исходного HEX (`Prefix + Command`).
   * Сформированного `ManufacturerData` (на Android).
   * Шести рассчитанных 16-битных `CBUUID` после XOR pre-whitening (на iOS).
4. **Тюнинг BLE-движка:** ручное изменение параметров `burstDurationMs` (по умолчанию $350\text{ мс}$), `stopBurstDurationMs` (по умолчанию $700\text{ мс}$) и минимального интервала обновления `minTxIntervalMs` (по умолчанию $180\text{ мс}$).

## 5. Спецификация протокола и BLE-движка

### 5.1. Общая логика передачи
Устройства семейства LoveSpouse не используют стандартное GATT-подключение. Управление осуществляется односторонней отправкой широковещательных пакетов **BLE Advertising** (non-connectable).

Полный логический пейлоад команды состоит из **11 байт**:
* **Префикс устройства (`prefix`):** 8 байт (например, `6D B6 43 CE 97 FE 42 7C`).
* **Код команды (`command`):** 3 байта (например, `E5 15 7D` — стоп, `E4 9C 6C` — режим 1, `E6 8E 4F` — максимум).

### 5.2. Реализация на Android (`BluetoothLeAdvertiser`)
* Используется `AdvertiseData.Builder().addManufacturerData(0xFFF0, payload)` где `payload` — массив из 11 байт (`prefix[0..7] + command[0..2]`).
* Параметры `AdvertiseSettings`:
  * `ADVERTISE_MODE_LOW_LATENCY` (интервал рекламы ~100 мс).
  * `ADVERTISE_TX_POWER_HIGH`.
  * `setConnectable(false)`.
  * `setTimeout(0)` (остановка управляется собственным таймером движка).
* Флаги `includeDeviceName(false)` и `includeTxPowerLevel(false)` строго отключены.

### 5.3. Реализация на iOS (`CBPeripheralManager` + Pre-Whitening XOR)
Поскольку `CoreBluetooth` запрещает сторонним приложениям передавать `Manufacturer Data`, применяется обходной механизм, совместимый с аппаратным приёмником устройств LoveSpouse: упаковка данных в список из шести 16-битных `Service UUID` с предварительным XOR-маскированием (компенсация сдвига BLE whitening).

**Алгоритм кодирования 11 байт (`raw = prefix[0..7] + command[0..2]`):**
1. Применить побитовый `XOR` каждого байта `raw[k]` с константной 11-байтовой маской `M`:
   $$M = [\texttt{94}, \texttt{BE}, \texttt{0A}, \texttt{ED}, \texttt{39}, \texttt{35}, \texttt{83}, \texttt{AD}, \texttt{8B}, \texttt{89}, \texttt{40}]$$
   $$E_k = \text{raw}_k \oplus M_k, \quad k \in \{0, \dots, 10\}$$
2. Дописать в конец 12-й байт-завершитель: $E_{11} = \texttt{0x0B}$.
3. Разбить 12 байт на 6 пар $(E_{2j}, E_{2j+1})$ для $j \in \{0, \dots, 5\}$.
4. Для каждой пары поменять байты местами (учёт Little-Endian при передаче в эфир) и сформировать 16-битный `CBUUID` из строки `HEX(E_{2j+1}) + HEX(E_{2j})`.

**Контрольный тестовый вектор (для обязательного Unit-теста):**
* Вход: `prefix = 6D B6 43 CE 97 FE 42 7C`, `command = E5 15 7D` (СТОП).
* После XOR + `0x0B`: `F9 08 49 23 AE CB C1 D1 6E 9C 3D 0B`.
* Ожидаемый массив из 6 `CBUUID`: `["08F9", "2349", "CBAE", "D1C1", "9C6E", "0B3D"]`.

**Жёсткие ограничения вызова `startAdvertising` на iOS:**
* В словарь передаётся **только** ключ `CBAdvertisementDataServiceUUIDsKey: uuids` (ровно 6 элементов).
* Запрещено добавлять `CBAdvertisementDataLocalNameKey` и любые другие поля (ломает смещение байт в радиопакете).
* Порядок UUID в массиве должен строго сохраняться (использовать `Array`, не `Set`).
* Приложение должно предупреждать пользователя (или автоматически предлагать OLED-замок), так как в фоновом режиме iOS переносит `ServiceUUIDs` в *overflow area*, делая пакет нечитаемым для игрушки.

### 5.4. Планировщик передачи (TX Scheduler) и квантование
1. **Квантование непрерывного сигнала:** для динамических режимов (Жест, Shake, Микрофон, Музыка, Автопилот, Funscript) входное значение $u \in [0, 1]$ преобразуется в индекс массива `intensityStepsHex` (длины $N$):
   $$i = \operatorname{round}(u \cdot (N - 1))$$
   При $u = 0$ всегда выбирается `stopCmdHex` (индекс $0$).
2. **Троттлинг и дедупликация:**
   * В динамических режимах пакет перезапускается **только при изменении целевого HEX-кода**.
   * Максимальная частота перезапуска рекламы ограничена **4–6 Гц** (интервал не менее $160\text{--}200\text{ мс}$), чтобы избежать системных ошибок `ADVERTISE_FAILED_TOO_MANY_ADVERTISERS` на Android и подвисаний `CBPeripheralManager` на iOS.
3. **Burst-режим (энергосбережение):**
   * Для одиночных команд (кнопки «Пульта») реклама запускается на `burstDurationMs` ($350\text{ мс}$), после чего автоматически вызывается `stopAdvertising()`, чтобы не разряжать батарею и не засорять эфир.
4. **Приоритетная очередь СТОП:**
   * Вызов `stop()` немедленно отменяет активный таймер burst, очищает очередь команд, останавливает активные генераторы/сенсоры и вещает `stopCmdHex` в течение `stopBurstDurationMs` ($700\text{ мс}$). Если у устройства несколько каналов — отправляется `stopCmdHex` для каждого активного канала (или общая команда стопа).

## 6. Сетевой слой и модель данных

### 6.1. Одноразовый импорт профиля по коду (API)
При добавлении устройства по коду выполняется единственный GET-запрос:
```http
GET http://lovespouse.zlmicro.com/index.php?g=App&m=Diyapp&a=getproductdetail&barcode={code}&userid=-1
```
* **Обработка безопасности сети:** поскольку эндпоинт работает по HTTP, в конфигурациях платформ (`NSAppTransportSecurity` на iOS и `network_security_config.xml` на Android) разрешение на незашифрованный трафик (Cleartext HTTP) выдаётся **исключительно для домена `lovespouse.zlmicro.com`**, а не глобально.
* **Кэширование:** полученный JSON парсится в локальную модель `DeviceProfile`, изображение устройства скачивается в локальное файловое хранилище приложения. После сохранения повторные запросы в сеть не требуются.
* **Отказоустойчивость:** таймаут запроса $8\text{ с}$; при недоступности сервера пользователь получает понятное сообщение с предложением выбрать профиль из встроенной оффлайн-базы.

### 6.2. Схема данных (Локальное хранилище)

## 7. Техническая архитектура и стек

### 7.1. Рекомендуемый технологический стек
* **Фреймворк:** **Flutter (Dart 3.x)** — оптимальный баланс скорости разработки, плавности кастомного UI (кривые, XY-пэд, FFT-визуализатор, анимации 60/120 FPS) и лёгкости сборки `.apk` / `.ipa`.
  *(Альтернатива: Kotlin Multiplatform + Compose Multiplatform, если приоритетом является отсутствие `MethodChannel`.)*
* **Управление состоянием:** Riverpod или BLoC (строгое разделение UI, движка паттернов и BLE-транспорта).
* **Локальная БД:** Drift (SQLite) или Hive + `flutter_secure_storage` для хранения хэша PIN-кода.
* **Нативные BLE-модули:** Swift (`CoreBluetooth`) для iOS и Kotlin (`android.bluetooth.le`) для Android, подключённые через единый `MethodChannel` (`com.pulselocal/ble_advertiser`).

### 7.2. Контракт нативного BLE-моста (`MethodChannel`)

| Метод (Dart → Native) | Аргументы | Назначение |
| :--- | :--- | :--- |
| `getBluetoothState` | — | Возвращает статус адаптера (`ready`, `poweredOff`, `unauthorized`, `unsupported`). |
| `broadcastCommand` | `prefixHex: String`, `commandHex: String`, `manufacturerId: Int`, `durationMs: Int` | Кодирует пакет под текущую ОС и вещает `durationMs` мс (0 = до следующей команды). |
| `broadcastStop` | `prefixHex: String`, `stopHex: String`, `manufacturerId: Int`, `durationMs: Int` | Прерывает текущую передачу и с высшим приоритетом вещает стоп-пакет. |
| `stopAdvertising` | — | Немедленно выключает BLE-рекламу. |
| `previewEncodedPacket` | `prefixHex: String`, `commandHex: String` | Возвращает отладочное представление пакета (сырой HEX или 6 `CBUUID`) для Debug Mode. |

### 7.3. Необходимые системные разрешения
* **Android:**
  * `BLUETOOTH_ADVERTISE` (Android 12+, runtime) — основной функционал.
  * `BLUETOOTH`, `BLUETOOTH_ADMIN` (для совместимости, `maxSdkVersion="30"`).
  * `INTERNET` — только для одноразового импорта профиля по коду.
  * `CAMERA` — запрашивается **только** при нажатии на сканер QR-кода.
  * `RECORD_AUDIO` — запрашивается **только** при первом входе в режим «Микрофон».
  * *Разрешение на геолокацию (`ACCESS_FINE_LOCATION`) НЕ запрашивать* (для BLE Advertising на Android 10+ без сканирования оно не требуется).
* **iOS (`Info.plist`):**
  * `NSBluetoothPeripheralUsageDescription` / `NSBluetoothAlwaysUsageDescription` — для отправки BLE-команд.
  * `NSCameraUsageDescription` — только при использовании QR-сканера.
  * `NSMicrophoneUsageDescription` — только при использовании режима «Микрофон».
  * `NSFaceIDUsageDescription` — только при включении биометрии в «Профиле».

## 8. Нефункциональные требования

1. **Размер дистрибутива:** установочный файл не более $25\text{--}35\text{ МБ}$.
2. **Скорость запуска:** «холодный старт» до отображения списка устройств $\le 1.0\text{ с}$.
3. **Задержка отклика (Latency):** время от нажатия кнопки режима в UI до старта излучения BLE-пакета $\le 50\text{ мс}$.
4. **Энергоэффективность:** автоматическое выключение BLE-рекламы после завершения burst-окна; истинный чёрный фон `#000000` в режиме OLED-замка.
5. **Приватность и нулевая телеметрия:** отсутствие сторонних аналитических SDK (Firebase Analytics, AppMetrica, Crashlytics и т.п.). Все логи Debug Mode хранятся исключительно в оперативной памяти (ring-buffer на последние 200 записей) и очищаются при закрытии приложения.

## 9. План разработки и критерии приёмки (Roadmap)

### Этап 1 — MVP: Ядро BLE, профили и базовый пульт
* **Задачи:**
  * Инициализация проекта, дизайн-система OLED Dark, навигация («Устройства» + «Профиль»).
  * Нативные BLE-модули на Kotlin (Android) и Swift (iOS с XOR pre-whitening) + юнит-тесты кодирования пакетов.
  * Импорт профиля через `zlmicro.com` (по коду и QR) + встроенная оффлайн-база пресетов.
  * Экран управления: вкладка «Пульт» (мультиканальность, сетка режимов, `Hold-to-Boost`), нижний док (`TX`, `СТОП`), режим «OLED-замок».
  * Базовый «Профиль» (визуал, экстренный стоп по кнопке громкости, скрытый вход в Debug Mode с HEX-инжектором и инспектором пакетов).
* **Критерии приёмки Этапа 1:**
  * Сырые пакеты, отправляемые Android- и iOS-сборками, верифицированы через анализатор **nRF Connect** и совпадают с эталонными векторами.
  * Реальное устройство стабильно реагирует на все команды (включая `СТОП` и `Hold-to-Boost`) с обеих платформ.
  * Приложение полностью работает в авиарежиме (с включённым Bluetooth) после сохранения профиля.

### Этап 2 — Креативные режимы и полноценный Debug Mode
* **Задачи:**
  * Режим «Жест» (1D-кривая, 2D XY-пэд, Loop, скорость).
  * Глобальная запись сессий (`REC`), библиотека и редактор (обрезка) в разделе «Ритмы».
  * Процедурный генератор «Автопилот (Wave / Chaos)».
  * Полная реализация «Сыщика команд (Command Hunter)» в Debug Mode с сохранением найденных режимов в профиль.
  * Приватность (PIN/FaceID, смена иконки) и Экспорт/Импорт базы в JSON.
* **Критерии приёмки Этапа 2:**
  * Динамические режимы держат стабильную частоту обновления $4\text{--}6\text{ Гц}$ без ошибок `BluetoothLeAdvertiser` на Android и без фризов UI на iOS.
  * Записанный ритм воспроизводится синхронно с записанными таймингами; экспорт и повторный импорт JSON полностью восстанавливают состояние приложения.

### Этап 3 — Сенсоры и опциональные модули
* **Задачи:**
  * Режим «Сенсоры»: Shake (акселерометр с EMA-сглаживанием), Микрофон (RMS + Noise Gate + AGC), локальный музыкальный плеер с FFT-анализом.
  * Опциональные модули (с тумблерами видимости в «Профиле»): таймер Кегеля и локальный видеоплеер с оверлеем управления и поддержкой `.funscript`.
* **Критерии приёмки Этапа 3:**
  * Все разрешения (камера, микрофон) запрашиваются строго по факту обращения к функции; отказ в разрешении не нарушает работу остальных режимов.
  * Локальный аудио- и видеоплеер стабильно синхронизируются с BLE-движком без рассинхронизации и утечек памяти при длительных сессиях ($> 30\text{ мин}$).
